# YunXi Linux 产品背景与决策层边界

> 本文是 `yunxi-agent-miyu` 的固定产品背景。它描述项目为什么存在、两个 YunXi
> 仓库分别扮演什么角色，以及后续能力应当如何进入当前产品基线。除非明确形成新的
> 产品决策，否则实现、评审和文档都应以本文为准。

## 1. 两个 YunXi 仓库的关系

### 历史参考：YunXi-Native

[YunXi-Native](https://github.com/sjxbbdb/YunXi-Native) 是历史参考版本。它用于参考
过去对 Linux 原生 Agent、Fish 接管、TUI、daemon、自然语言终端交互和系统级 Agent
方向的设计与实现经验。

它不是当前产品的开发基线，也不是后续要直接复制或重新合并的代码树。需要借鉴时，
先提取设计意图和可验证经验，再在当前基线上重新实现和测试。

### 当前基线：yunxi-agent-miyu

[yunxi-agent-miyu](https://github.com/sjxbbdb/yunxi-agent-miyu) 是当前正在演进的
产品仓库。它 Fork 自
[SHORiN-KiWATA/miyu-agent](https://github.com/SHORiN-KiWATA/miyu-agent)，未来的
开发、测试、问题修复和发布都以这个仓库为准。

Miyu 提供 Linux 原生交互底座，YunXi 在其上逐步增加人格、灵魂、用户画像、记忆、
知识库和陪伴能力。这个关系不是“大融合”，而是以 Miyu 为身体和行动层，逐步形成
YunXi 的内在与产品体验。

Windows/Web/语音方向的历史实现仍可在
[YunXi-Agent](https://github.com/sjxbbdb/YunXi-Agent) 查阅，但不属于当前 Linux
产品的主开发线。

## 2. 产品目标

YunXi Linux 不是一个换皮的聊天窗口，也不是一个只会生成 Shell 命令的包装器。
它的目标是成为一个长期运行在 Linux 上的陪伴型通用系统级 Agent：

```text
人类表达意图
      ↓
终端 / Fish / TUI 接入
      ↓
YunXi 理解上下文与用户
      ↓
Miyu 的 Linux Runtime 规划、授权与执行
      ↓
文件、进程、服务、包管理、MCP、Skills 与系统工具
      ↓
以 YunXi 的人格和陪伴方式返回结果
```

Linux 的重新定义不在于隐藏终端，而在于给终端增加一层自然语言交互层：用户不必
先记住命令、参数、路径和管道，而是可以直接描述目标；系统仍然保持开放、可组合、
可审计和可控。

## 3. 能力分层

### Miyu 底座：身体与行动能力

- Fish 终端接管和终端生命周期；
- 用户级 daemon、Unix socket 与 IPC；
- TUI、REPL、会话和事件回放；
- Shell、文件、进程、服务、软件包等 Linux 工具；
- MCP、Skills、多 Agent、Sandbox 和工具执行；
- Linux 知识库与终端工作流。

这些能力已经经过 Miyu 的 Linux 方向验证，除非实机测试证明必须改变，否则不重复
实现、不复制一套新的 Runtime。

### YunXi 层：内在与陪伴能力

- Persona、Soul、语气、边界和称呼；
- 用户画像和关系阶段；
- 短期上下文、长期经历、关系记忆和主动关怀；
- 情绪线索、陪伴策略、情书与信箱；
- 让工具执行结果变成稳定、自然、连续的人类式回应。

YunXi 层不能绕过 Miyu 的真实执行、授权和系统边界。人格可以影响理解方式和表达
方式，但不能凭空获得系统权限。

## 4. 记忆与知识边界

记忆库和知识库必须保持独立：

| 空间 | 内容 | 主要存储 | 召回目的 |
| --- | --- | --- | --- |
| 用户档案 | 稳定身份、偏好、称呼和明确授权信息 | 结构化记录 | 直接注入或精确读取 |
| 短期记忆 | 当前会话语气、情景和未完成上下文 | 会话状态 | 承接下一轮对话 |
| 长期记忆 | 用户经历、项目事实、关系事件和经过确认的偏好 | 独立向量记忆库 + 元数据 | 语义召回 |
| 知识库 | Linux 命令、系统知识和用户授权的私有知识 | 独立向量知识库 + 来源 | 问题解决和工具规划 |

用户说出的每一句话都不是长期记忆。写入长期向量库之前，必须经过“是否值得长期
保存”的判断；无关闲聊、一次性指令、临时状态和敏感内容应被跳过、短期保留或要求
确认。记忆写入还必须保留来源、时间、作用域、置信度、敏感性和可撤销信息。

## 5. Laya 决策层：候选方向，不是当前依赖

Laya 是 Convai Innovations 发布的开源 System 1 决策模型。它不是文本生成模型，
而是对给定状态和结构化问题一次前向计算，返回 `choice`、`score`、`noul` 等类型
化判断和概率。官方模型卡提供英文、multilingual 和 typed-decisions 方向，权重
采用 Apache-2.0；Node/TypeScript 侧已有 ONNX Runtime 封装可供参考。

- [Laya 官方模型卡](https://huggingface.co/convaiinnovations/laya)
- [Laya 的 ONNX Runtime 封装参考](https://github.com/receptron/laya)

它适合做“快速判断”，不适合替代 YunXi 的主模型，也不应直接承担系统权限。计划中
的决策模型接口应当是窄的、可替换的，例如：

```text
DecisionPort
  ├─ decide_memory_admission
  ├─ decide_compact_salience
  ├─ decide_retrieval_relevance
  ├─ decide_tool_route
  └─ decide_proactive_follow_up
```

### 预期判断点

1. **上下文压缩**：判断哪些事实、目标、约束和未完成事项必须保留，哪些内容可以
   合并或降级。
2. **长期记忆写入**：判断消息是否值得长期保存、属于哪类记忆、作用域和大致保留
   周期；低置信度进入候选区，不直接写入向量库。
3. **记忆召回**：在向量检索候选中判断哪些内容真正与当前问题相关，减少无关记忆
   污染主模型上下文。
4. **工具与终端路径**：判断是普通 Shell 命令、自然语言任务、知识查询还是需要
   YunXi 进一步澄清；它只能建议路径，不能替代执行层的权限判断。
5. **陪伴动作**：判断是否需要主动关怀、提醒或写信，但不得把低置信度推断伪装成
   用户事实。

### 必须保留的边界

- 决策模型只做建议，不拥有工具审批、Sandbox 或系统权限；
- 低置信度、模型不可用或输入超出范围时，回退到确定性规则、主模型或询问用户；
- 不把 API 密钥、原始凭证和不必要的敏感内容发送给决策模型；
- 决策结果记录模型版本、问题版本、输入摘要和置信度，便于复盘和回滚；
- Laya 的概率不能直接当作真实置信度使用，必须用 YunXi 自己的中文和 Linux 数据
  做校准与验收；
- 决策模型不能破坏现有的 append-only、上下文化石化和缓存字节契约。它可以帮助
  规划下一次 compact，但不能修改已经发送并存档的历史前缀。

### 接入顺序

1. **离线评测**：用现有会话、记忆候选、compact 样本建立人工标注集。
2. **Shadow Mode**：Laya 只给出判断并记录，不影响真实运行结果，与规则/主模型
   结果对比。
3. **记忆候选门**：先只控制长期记忆候选，不直接删除短期上下文。
4. **召回重排**：确认中文和 Linux 术语上的精度后，再用于向量候选重排。
5. **压缩辅助**：最后才进入 compact 规划，并保留完整回退路径。

在完成中文、Linux 终端语境和隐私边界的实测前，Laya 只能作为候选决策层，不应被
写成 YunXi Runtime 的硬依赖。

## 6. 当前不可改变的判断

- 当前产品基线是 `yunxi-agent-miyu`；
- `YunXi-Native` 是历史参考，不是当前源码基线；
- Miyu 负责 Linux 原生交互和可靠执行；
- YunXi 负责人格、灵魂、用户理解和陪伴；
- 记忆库与知识库分离；
- 决策模型是可替换的辅助层，不是新的主模型；
- 所有新增能力必须在真实 WSL/Arch Linux 环境中验证后，才决定是否成为默认行为。
